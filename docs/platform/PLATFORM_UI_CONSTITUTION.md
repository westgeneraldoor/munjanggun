# Platform UI Constitution

이 문서는 문장군 플랫폼 화면을 만들거나 수정할 때의 헌법이다. 기능 구현보다 먼저 고객 여정, 운영자 업무, 공통 UI 규칙을 확인한다.

## 1. 한 제품처럼 보이게 만든다

- 무료방문 실측견적 상담, A/S 접수, 마이페이지, 어드민은 각각 다른 실험 화면이 아니라 하나의 문장군 플랫폼이다.
- 같은 성격의 화면은 같은 프레임을 쓴다. 고객 접수 화면은 상단바, 로딩 화면, 완료 화면, 이전/홈/마이페이지 동선이 동일해야 한다.
- 화면 이름은 실제 업무와 맞춘다. 예: 품목과 방문일 설정은 `견적 접수 운영설정`이지 추상적인 `플랫폼 운영 설정`이 아니다.
- 메뉴명, 페이지 제목, 버튼명, 완료 문구가 서로 다른 말을 하면 수정 전 실패로 본다.

## 2. 상태와 버튼은 겹쳐도 읽혀야 한다

- 모든 버튼은 `default`, `hover`, `active`, `active:hover`, `disabled`, `focus-visible` 상태를 따로 확인한다.
- 선택된 버튼 위에 마우스를 올려도 텍스트와 배경 대비가 유지되어야 한다.
- 밝은 금색 배경에 흰색 텍스트를 얹지 않는다. 선택 상태에서 흰색 텍스트를 써야 한다면 배경을 충분히 어둡게 조정해 WCAG AA 대비를 확보한다.
- 삭제가 아닌 숨김/비노출 동작에는 휴지통 아이콘을 쓰지 않는다. `EyeOff`, `Eye`처럼 실제 의미와 맞는 아이콘을 쓴다.

## 3. 고객 화면 원칙

- 고객은 문장군에 가입하기 위해 오는 것이 아니라 상담, 확인, 수리, 결제 여정을 이어가기 위해 온다.
- 고객 접수 화면은 불안을 줄이고 다음 행동을 돕는 톤을 유지한다.
- 무료방문 실측견적 상담과 A/S 접수는 공통 접수 패턴을 공유한다. 새 접수 유형을 만들 때는 먼저 기존 공통 프레임을 재사용한다.
- 모바일 390px에서 좌우 스크롤이 생기면 실패다.
- 완료 화면에서 고객이 홈, 마이페이지, 다음 행동으로 빠져나갈 수 있어야 한다.

## 4. 어드민 화면 원칙

- 어드민은 운영자가 반복해서 처리하는 업무 도구다. 장식보다 밀도, 스캔, 정렬, 빠른 반응을 우선한다.
- 데스크탑은 목록을 보며 상세를 빠르게 바꾸는 구조를 우선한다.
- 모바일은 목록 카드와 상세 화면 전환을 분리한다. 데스크탑 우측 상세 패널을 모바일에 그대로 밀어 넣지 않는다.
- 버튼은 업무 단위로 묶고, 행 안 버튼이 내용보다 커 보이거나 줄마다 흔들리면 실패다.
- 접수 큐의 큰 필터는 `전체 / 무료실측 / A/S / 결제`, 보조 필터는 `전체 / 확인필요 / 확인완료`를 기준으로 한다.

## 5. 검수 의무

UI 변경 후 최소 검수:

- `npm run lint`
- `npm run build`
- Playwright 또는 브라우저로 모바일 390px, 데스크탑 1366px 스크린샷 확인
- 좌우 overflow 확인: `document.documentElement.scrollWidth <= window.innerWidth`
- 버튼 상태 확인: hover, selected, selected hover, disabled
- 메뉴명, 페이지 제목, 버튼명, 빈 상태/완료 문구 일치 확인

검수 없이 “완료”라고 말하지 않는다.

## 6. 작업 전 체크

새 UI를 만들거나 바꿀 때 먼저 답한다.

- 이 화면은 고객 여정인가, 운영자 업무인가?
- 이미 같은 성격의 화면이 있는가?
- 공통 프레임/로딩/상단바/완료 화면을 재사용했는가?
- 모바일과 데스크탑에서 각각 자연스러운가?
- 글자, 버튼, 배지가 겹치거나 사라지는 상태가 없는가?

위 질문 중 하나라도 아니면 코드를 더 쓰기 전에 구조를 먼저 고친다.
