# Decision Log

## 2026-06-10 - 플랫폼 UI 헌법과 closeout 기준

### 결정

고객 포털, 고객 접수, 플랫폼 어드민 UI를 수정할 때는 `docs/platform/PLATFORM_UI_CONSTITUTION.md`를 기준으로 삼는다.

- 같은 성격의 고객 접수 화면은 상단바, 로딩, 완료 화면, 홈/마이페이지 동선을 공유한다.
- 버튼은 `default`, `hover`, `active`, `active:hover`, `disabled`, `focus-visible` 상태에서 텍스트 대비를 확인한다.
- 화면 이름, 메뉴명, 버튼명은 실제 업무명과 맞춘다.
- 어드민은 장식보다 밀도, 스캔, 정렬, 빠른 반응을 우선한다.
- 모바일 390px에서 좌우 overflow가 생기면 완료로 보지 않는다.

### 이유

MVP-02 보강 과정에서 무료견적과 A/S 접수 화면의 프레임, 로딩, 완료 동선이 서로 달라졌고, 어드민 필터 active-hover 상태에서 글자 대비가 무너지는 문제가 발생했다. 이런 문제는 기능 구현 문제가 아니라 제품 일관성과 검수 기준 문제이므로 재발 방지 기준을 문서화한다.

### 되돌릴 조건

향후 정식 디자인 시스템이 별도 토큰/컴포넌트 체계로 정리되면 이 문서는 상위 디자인 시스템 문서로 흡수한다. 단, 버튼 상태 대비와 공통 접수 프레임 원칙은 유지한다.

## 2026-06-04 - MVP-02 guided estimate intake decision

무료방문 실측견적 상담 신청은 단일 긴 폼이 아니라, 고객이 안심하면서 단계별로 완료할 수 있는 guided intake로 운영한다.

- 핵심 안내 문구는 `무료방문 실측견적 상담은 무료입니다.`로 유지한다.
- 신청자와 실제 연락받을 사람이 다른 상황을 기본 케이스로 포용한다.
- 집주인, 세입자, 배우자 등 복수 연락 대상은 추가 연락처로 남길 수 있게 한다.
- 방문 시간은 직접 선택하지 않고, 방문 전날 오후 4~5시 코스 마감 후 담당자가 직접 안내한다.
- 전화 부재 시 문자 안내, 시간이 맞지 않을 경우 일정 변경 가능성을 고객 언어로 안내한다.
- 천안, 아산, 청주, 세종, 대전은 수요일/토요일 중심 방문일만 선택하게 한다.
- 방문 상담 가능 지역 밖 주소는 접수 단계에서 막고, DB trigger에서도 저장을 차단한다.

근거: 기능이 작동하더라도 인스타 유입 고객이 첫 신청 화면에서 불안하거나 번거롭게 느끼면 MVP-02는 실제 영업 흐름으로 성공하기 어렵다. 접수 화면은 문장군 플랫폼의 첫 고객 경험이므로, 문구, 글자 크기, 화면 톤, 진행 방식까지 고객 여정 기준으로 설계한다.

참고: 2026-05-30 이후 플랫폼 MVP 기준은 "MVP-01 카카오 로그인", "MVP-02 무료방문견적 신청 + 어드민 접수 큐", private `measurement-media` bucket이다. 아래 과거 결정의 이전 표현은 이 최신 결정으로 보정해서 해석한다.

## 2026-06-04 — MVP-02 고객 신청 UX 최종 보정 원칙

### 결정

MVP-02 무료방문 실측 견적상담 신청 화면은 기능이 돌아가는 것만으로 완료하지 않는다.

고객 연령대와 실제 신청 상황을 기준으로, 누를 수 있는 것은 누를 수 있게 보여야 하고, 접혀 있는 안내는 열었을 때 실제 운영 안내로 충분히 상세해야 한다.

- 고객 포털로 돌아가는 버튼은 역할이 명확한 문구와 아이콘으로 표시한다.
- 신청 전 확인사항은 버튼처럼 인식되도록 강조한다.
- 가능 지역, 충청권 지정 요일, 접수 마감 시간, 방문 시간 안내, FAQ를 고객 언어로 풀어 쓴다.
- 충청권은 천안, 아산, 대전, 세종, 청주를 수요일과 토요일 중심으로 운영한다고 구체적으로 안내한다.
- 방문시간대 선택은 제거한다. 정확한 방문 시간은 회사가 전날 동선을 잡아 안내하는 운영 방식과 충돌하기 때문이다.
- 상담 희망 내용은 필수가 아니라 선택사항으로 둔다.
- 추천인 입력란을 선택사항으로 추가한다.
- 주소 검색이 blank로 보일 때 고객이 막히지 않도록 새 창 검색과 수동 입력 fallback을 제공한다.
- 플랫폼 화면에는 이모지를 사용하지 않는다.
- 다크 UI는 유지할 수 있으나 본문, 입력, 버튼 대비를 고객이 읽기 쉬운 수준으로 올린다.

### 이유

문장군 플랫폼의 목적은 고객을 복잡한 쇼핑몰 회원가입으로 끌고 가는 것이 아니라, 무료방문 실측 견적상담 신청을 편하고 정확하게 완료하게 만드는 것이다.

운영 안내가 흐릿하면 고객은 신청 전에 불안해지고, 주소 검색이나 달력에서 막히면 바로 이탈한다. 반대로 신청 데이터가 너무 자유입력으로 들어오면 어드민과 AppSheet 수동 등록 업무가 어려워진다.

따라서 고객 화면은 쉽고, 어드민 데이터는 정돈되게 받는 쪽을 기준으로 둔다.

### 되돌릴 조건

실제 고객 테스트에서 신청 전 안내가 길어 이탈을 만든다면 기본 화면에는 핵심 3줄만 남기고, 상세 안내는 접힌 상태로 유지한다. 단, 가능 지역과 방문시간 운영 방식은 반드시 접근 가능해야 한다.

## 2026-06-02 — 무료실측 신청 UX 운영화 원칙

### 결정

MVP-02 기본 신청 흐름 검수 후, MVP-03 담당자 배정으로 바로 넘어가지 않고 MVP-02.1을 먼저 진행한다.

무료방문 실측 견적상담 신청에서 주소, 방문 희망일, 관심 제품 카테고리는 자유 텍스트/하드코딩으로 두지 않는다.

- 주소는 Daum/Kakao 주소 검색 기반으로 받는다.
- 방문 희망일은 달력 선택으로 받는다.
- 신청 가능 날짜는 어드민에서 최소/최대 접수 가능일, 토요일, 일요일, 공휴일, 특정 날짜 예외로 통제한다.
- 관심 제품 카테고리는 다중 선택이며, 품목은 어드민에서 추가, 삭제, 순서 변경할 수 있어야 한다.

### 이유

고객이 편하게 신청해야 플랫폼 전환이 일어난다. 자유입력 주소와 텍스트 일정은 고객에게는 불편하고, 운영자에게는 AppSheet 수동 등록과 일정 관리 오류를 만든다.

문장군 플랫폼의 실무 중심은 어드민이므로, 고객 신청 폼의 선택지는 운영자가 관리할 수 있어야 한다.

### 되돌릴 조건

Daum/Kakao 주소 검색이나 달력 UI가 고객 연령대에서 오히려 이탈을 만들면, 주소 검색은 유지하되 수동 보정 입력을 보조 수단으로 열고, 날짜 선택 UI는 더 단순한 빠른 선택 버튼과 병행한다.

## 2026-06-02 — MVP-01 카카오 로그인 검증 완료와 보조 로그인 원칙

### 결정

MVP-01 카카오 로그인 기반은 로컬 OAuth 테스트와 Supabase MCP 검증을 통과한 것으로 판정한다.

고객 profile 생성 기준은 `platform.profiles.role = customer`이며, 신규 auth user와 기존 auth user 재로그인 모두 profile 보정 생성이 되어야 한다.

고객용 이메일 로그인은 필요성을 인정하되, 비밀번호 회원가입을 기본값으로 열지 않는다. 보조 로그인은 매직링크 또는 OTP 방식을 우선 검토한다.

전화번호는 Kakao OAuth에서 안정적으로 받지 않고, MVP-02 무료방문견적 신청 폼에서 필수 입력으로 확보한다.

### 검증

- 로컬 Kakao OAuth 로그인 후 `/portal` 진입 확인
- Supabase MCP로 `platform.profiles.role = customer` row 생성 확인
- `auth.users` UPDATE trigger로 기존 auth user 재로그인 시 profile 보정 확인
- `platform` schema exposed 확인
- `platform_private` schema 미노출 유지

### 이유

문장군 플랫폼의 목적은 쇼핑몰식 회원가입이 아니라 무료방문견적 상담 여정으로 고객을 자연스럽게 연결하는 것이다.

카카오를 기본 로그인으로 두되, 카카오 미사용 고객과 장애 상황을 대비해 이메일 보조 수단은 필요하다. 다만 비밀번호 회원가입은 고객 마찰과 운영 부담을 늘릴 수 있어 MVP 기본값으로 두지 않는다.

### 되돌릴 조건

실제 고객 테스트에서 카카오 로그인 전환율이 낮거나 이메일 미제공/카카오 미사용 고객 이탈이 반복되면, MVP-01.5 또는 MVP-02 범위에서 이메일 매직링크/OTP를 우선 구현한다.

## 2026-05-30 — AI 작업 분담과 중복 검증 최소화

### 결정

문장군 플랫폼 개발에서 Gemini Flash 3.5 High를 기본 구현 작업자로 둔다.

Codex는 중복 실행자가 아니라 총괄 PM/감리자로 둔다. Codex는 오더 작성, 설계 판단, diff 검수, 위험 구간 재검증, 커밋/PR 정리를 맡는다.

Claude Opus/Thinking은 고정 작업자가 아니다. 사용자 또는 Codex가 필요하다고 판단할 때만 감리, 레드팀, 고위험 설계 리뷰 용도로 호출한다.

### 검증 원칙

- `npm run lint`, `npm run build`, 기본 스모크 테스트는 작업자가 먼저 실행하고 결과를 남긴다.
- Codex는 매번 같은 명령을 중복 실행하지 않는다.
- Codex는 Auth/RBAC/Storage/Payment, 실패/불확실한 보고, PR 머지 전, 배포 전에는 직접 재검증할 수 있다.
- 커밋, 푸시, 배포, 릴리즈는 반드시 Codex만 하는 일이 아니다. 다만 PR 본문, 최종 diff, 머지 전 판단은 Codex가 맡는 것을 기본으로 한다.

### 이유

사용자는 Gemini 유료 계정 여러 개와 Codex 계정을 함께 활용한다. 따라서 작업 속도와 토큰 효율을 위해 Gemini가 구현과 1차 검증을 맡고, Codex는 총괄 감리와 최종 판단에 집중하는 편이 낫다.

### 되돌릴 조건

작업자 검증 보고가 반복적으로 부정확하거나, 고위험 작업에서 회귀가 발생하면 Codex의 직접 재검증 범위를 넓히고 Claude 감리 호출 빈도를 높인다.

## 2026-05-30 — 어드민 중심 플랫폼 MVP와 결제 이후 자산화

### 결정

플랫폼 MVP의 실무 중심을 어드민 운영 콘솔로 둔다.

고객뷰는 무료방문견적 신청, 견적 확인, 결제를 쉽게 만드는 입구이고, 어드민은 접수 확인, AppSheet 수동 등록, 담당자 배정, 견적서 작성, 결제 확인, 후기 요청, AS 접수 처리를 담당하는 실제 운영 엔진이다.

### 확정 사항

- MVP-01 로그인은 카카오만 구현한다.
- Google/Naver 간편로그인은 후속 확장 시점에 함께 검토한다.
- 무료방문견적 신청과 AS 접수는 로그인 필수다.
- 고객 가입 시 이름과 휴대폰 번호는 필수다.
- 신청 사진/영상은 선택사항이지만, 사진 여러 장 동시 선택과 동영상 첨부를 지원한다.
- 결제는 토스페이먼츠로 진행한다.
- 결제 전 짧은 설문을 필수로 두고, 객관식 버튼과 직접입력을 함께 제공한다.
- 설문 질문/선택지는 어드민에서 추가, 삭제, 관리할 수 있어야 한다.
- 반복되는 직접입력 응답은 정식 선택지로 승격할 수 있어야 한다.
- 견적서는 플랫폼 어드민에서 영업 담당자가 템플릿 기반으로 작성한다.
- AppSheet는 MVP에서 수동 등록으로 유지하고, 장기적으로 연동/흡수 전략을 별도 과제로 둔다.
- 시공 이후에는 AS 접수, 후기, 시공 완료 사진, 홍보 활용 동의를 통해 플랫폼에 남는 자산을 만든다.

### 이유

문장군의 사내 운영 ERP는 이미 AppSheet에 크게 구축되어 있다. 플랫폼이 이를 즉시 대체하려고 하면 MVP가 무거워진다.

초기 플랫폼은 인스타 유입 고객을 카카오 로그인, 무료방문견적 신청, 어드민 접수 큐, 견적 링크, 토스 결제까지 연결하고, 운영자는 그 정보를 AppSheet에 수동 등록할 수 있어야 한다.

### 되돌릴 조건

어드민 접수 큐가 AppSheet 수동 등록 업무를 줄이지 못하거나 오히려 이중 입력을 늘리면, MVP-02 이후 어드민 UI를 먼저 개선하고 자동화/n8n/API 연동은 뒤로 미룬다.

앞으로 PM과 작업자는 `docs/platform/PLATFORM_TASKS.md`에서 전체 일정 순서를 확인하고, `_order.md`에서 현재 작업 오더만 실행한다.

### 되돌릴 조건

문서 이동으로 에이전트가 기준 문서를 찾지 못하거나 자동화가 깨지면 루트 진입 문서에 별도 인덱스를 추가한다. 단, 플랫폼 태스크 보드를 `PROJECT_TASKS.md`에 다시 길게 합치지는 않는다.

## 2026-05-29 — 플랫폼 전략 문서 최상위 기준화

### 결정

`docs/platform/PLATFORM_STRATEGY.md`를 플랫폼 작업의 최상위 기준 문서로 둔다.

문장군 플랫폼의 목적은 쇼핑몰 구축이 아니라 고객 여정 통합이다.

### 이유

`docs/platform/PLATFORM_MIGRATION_AUDIT.md`는 기술/문서/코드 승계 관점의 감사로는 충분하지만, 고객이 왜 네이버예약 대신 문장군 플랫폼에서 무료방문견적을 신청해야 하는지에 대한 사업 전략 기준이 부족했다.

앞으로 장바구니, 쿠폰, 포인트, 회원등급, 자동견적 같은 기능 제안이 나올 때 `docs/platform/PLATFORM_STRATEGY.md`를 기준으로 컷하거나 후순위화한다.

### 실행 순서

1. `docs/platform/PLATFORM_DB_RBAC_DESIGN.md`를 MVP-01/02에 필요한 최소 범위로 작성한다.
2. MVP-01 카카오 로그인을 구현한다.
3. MVP-02 무료방문견적 신청 + 어드민 접수 큐를 구현한다.
4. 관리자/영업 매니저 접수 확인과 담당자 배정으로 확장한다.

### 되돌릴 조건

실제 고객 신청 테스트에서 플랫폼 신청 전환이 네이버예약 대비 명확히 낮고, CTA/폼/로그인 마찰 개선 후에도 회복되지 않으면 플랫폼 신청을 보조 경로로 낮추고 네이버예약 중심 운영을 유지한다.

# 2026-06-04 - MVP-02 public showroom entry decision

## Decision

The existing showroom is part of the platform Public Experience, so the main floating `무료방문견적` CTA should enter the MVP-02 platform application flow at `/portal/measure/new`, not the external Naver reservation link.

The public showroom must also expose a minimal top-right auth entry: signed-out users see `로그인`, signed-in customers see `마이페이지` and `무료방문견적 신청`, and signed-in administrators also see `플랫폼 어드민`.

## Reason

MVP-02 is not realistically testable if customers and reviewers cannot enter the new application flow from the visible public showroom. The entry point should match the actual customer journey before MVP-03 operational status work begins.
