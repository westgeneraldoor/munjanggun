# Decision Log

참고: 2026-05-30 이후 플랫폼 MVP 기준은 "MVP-01 카카오 로그인", "MVP-02 무료방문견적 신청 + 어드민 접수 큐", private `measurement-media` bucket이다. 아래 과거 결정의 이전 표현은 이 최신 결정으로 보정해서 해석한다.

## 2026-05-30 — AI 작업 분담과 중복 검증 최소화

### 결정

문장군 플랫폼 개발에서 Gemini Flash 3.5 High를 기본 구현 작업자로 둔다.

Codex는 중복 실행자가 아니라 총괄 PM/감리자로 둔다. Codex는 오더 작성, 설계 판단, diff 검수, 위험 구간 재검증, 커밋/PR 정리를 맡는다.

Claude Opus/Thinking은 고정 작업자가 아니다. 사용자 또는 Codex가 필요하다고 판단할 때만 감리, 레드팀, 고위험 설계 리뷰 용도로 호출한다.

### 검증 원칙

- `npm run lint`, `npm run build`, 기본 스모크 테스트는 작업자가 먼저 실행하고 결과를 남긴다.
- Codex는 매번 같은 명령을 중복 실행하지 않는다.
- Codex는 Auth/RBAC/Storage/Payment, 실패/불확실한 보고, PR 머지 전, 배포 전에는 직접 재검증할 수 있다.
- 커밋, 푸시, 배포, 릴리즈는 반드시 Codex만 하는 일이 아니다. 다만 PR 본문, 최종 diff, 머지 전 판단은 Codex가 맡는 것을 기본으로 한다.

### 이유

사용자는 Gemini 유료 계정 여러 개와 Codex 계정을 함께 활용한다. 따라서 작업 속도와 토큰 효율을 위해 Gemini가 구현과 1차 검증을 맡고, Codex는 총괄 감리와 최종 판단에 집중하는 편이 낫다.

### 되돌릴 조건

작업자 검증 보고가 반복적으로 부정확하거나, 고위험 작업에서 회귀가 발생하면 Codex의 직접 재검증 범위를 넓히고 Claude 감리 호출 빈도를 높인다.

## 2026-05-30 — 어드민 중심 플랫폼 MVP와 결제 이후 자산화

### 결정

플랫폼 MVP의 실무 중심을 어드민 운영 콘솔로 둔다.

고객뷰는 무료방문견적 신청, 견적 확인, 결제를 쉽게 만드는 입구이고, 어드민은 접수 확인, AppSheet 수동 등록, 담당자 배정, 견적서 작성, 결제 확인, 후기 요청, AS 접수 처리를 담당하는 실제 운영 엔진이다.

### 확정 사항

- MVP-01 로그인은 카카오만 구현한다.
- Google/Naver 간편로그인은 후속 확장 시점에 함께 검토한다.
- 무료방문견적 신청과 AS 접수는 로그인 필수다.
- 고객 가입 시 이름과 휴대폰 번호는 필수다.
- 신청 사진/영상은 선택사항이지만, 사진 여러 장 동시 선택과 동영상 첨부를 지원한다.
- 결제는 토스페이먼츠로 진행한다.
- 결제 전 짧은 설문을 필수로 두고, 객관식 버튼과 직접입력을 함께 제공한다.
- 설문 질문/선택지는 어드민에서 추가, 삭제, 관리할 수 있어야 한다.
- 반복되는 직접입력 응답은 정식 선택지로 승격할 수 있어야 한다.
- 견적서는 플랫폼 어드민에서 영업 담당자가 템플릿 기반으로 작성한다.
- AppSheet는 MVP에서 수동 등록으로 유지하고, 장기적으로 연동/흡수 전략을 별도 과제로 둔다.
- 시공 이후에는 AS 접수, 후기, 시공 완료 사진, 홍보 활용 동의를 통해 플랫폼에 남는 자산을 만든다.

### 이유

문장군의 사내 운영 ERP는 이미 AppSheet에 크게 구축되어 있다. 플랫폼이 이를 즉시 대체하려고 하면 MVP가 무거워진다.

초기 플랫폼은 인스타 유입 고객을 카카오 로그인, 무료방문견적 신청, 어드민 접수 큐, 견적 링크, 토스 결제까지 연결하고, 운영자는 그 정보를 AppSheet에 수동 등록할 수 있어야 한다.

### 되돌릴 조건

어드민 접수 큐가 AppSheet 수동 등록 업무를 줄이지 못하거나 오히려 이중 입력을 늘리면, MVP-02 이후 어드민 UI를 먼저 개선하고 자동화/n8n/API 연동은 뒤로 미룬다.

## 2026-05-30 — 플랫폼 문서 구조와 태스크 보드 분리

### 결정

플랫폼 제작 일정의 기준 문서를 `docs/platform/PLATFORM_TASKS.md`로 분리한다.

루트의 `PROJECT_TASKS.md`는 기존 V2 쇼룸 히스토리와 전체 상태 포인터로 유지하고, 플랫폼의 세부 페이즈/오더/완료 기준은 `docs/platform/PLATFORM_TASKS.md`를 우선한다.

### 문서 구조

- 플랫폼 기준 문서: `docs/platform/`
- 쇼룸 기준 문서: `docs/showroom/`
- 과거 감사/출시/아카이브: `docs/archive/showroom/`
- 실행 진입점: `GEMINI.md`, `_context.md`, `_order.md`, `PROJECT_TASKS.md`

### 이유

플랫폼 개발이 시작되면서 루트에 PRD, 감사, 아카이브, 에이전트 문서가 뒤섞여 현재 일정이 잘 보이지 않았다.

앞으로 PM과 작업자는 `docs/platform/PLATFORM_TASKS.md`에서 전체 일정 순서를 확인하고, `_order.md`에서 현재 작업 오더만 실행한다.

### 되돌릴 조건

문서 이동으로 에이전트가 기준 문서를 찾지 못하거나 자동화가 깨지면 루트 진입 문서에 별도 인덱스를 추가한다. 단, 플랫폼 태스크 보드를 `PROJECT_TASKS.md`에 다시 길게 합치지는 않는다.

## 2026-05-29 — 플랫폼 전략 문서 최상위 기준화

### 결정

`docs/platform/PLATFORM_STRATEGY.md`를 플랫폼 작업의 최상위 기준 문서로 둔다.

문장군 플랫폼의 목적은 쇼핑몰 구축이 아니라 고객 여정 통합이다.

### 이유

`docs/platform/PLATFORM_MIGRATION_AUDIT.md`는 기술/문서/코드 승계 관점의 감사로는 충분하지만, 고객이 왜 네이버예약 대신 문장군 플랫폼에서 무료방문견적을 신청해야 하는지에 대한 사업 전략 기준이 부족했다.

앞으로 장바구니, 쿠폰, 포인트, 회원등급, 자동견적 같은 기능 제안이 나올 때 `docs/platform/PLATFORM_STRATEGY.md`를 기준으로 컷하거나 후순위화한다.

### 실행 순서

1. `docs/platform/PLATFORM_DB_RBAC_DESIGN.md`를 MVP-01/02에 필요한 최소 범위로 작성한다.
2. MVP-01 카카오 로그인을 구현한다.
3. MVP-02 무료방문견적 신청 + 어드민 접수 큐를 구현한다.
4. 관리자/영업 매니저 접수 확인과 담당자 배정으로 확장한다.

### 되돌릴 조건

실제 고객 신청 테스트에서 플랫폼 신청 전환이 네이버예약 대비 명확히 낮고, CTA/폼/로그인 마찰 개선 후에도 회복되지 않으면 플랫폼 신청을 보조 경로로 낮추고 네이버예약 중심 운영을 유지한다.

## 2026-05-29 — MVP-01/02 DB/RBAC 최소 설계 확정

### 결정

`docs/platform/PLATFORM_DB_RBAC_DESIGN.md`를 MVP-01 카카오 로그인, MVP-02 무료방문견적 신청, MVP-03 담당자 배정 기반의 최소 DB/RBAC 설계 문서로 둔다.

### 핵심 설계

- 기존 `showroom` 스키마는 Public Experience CMS로 유지한다.
- 신규 플랫폼 데이터는 `platform` 스키마에 둔다.
- 역할은 `customer`, `sales_manager`, `administrator`로 시작한다.
- 고객 현장 사진/영상은 공개 버킷이 아니라 private `measurement-media` bucket과 signed URL로 처리한다.
- MVP-01은 Kakao만 구현하고, Google/Naver 간편로그인은 후속 확장 시점에 함께 검토한다.

### 다음 실행

MVP-01 카카오 로그인 구현 오더를 작성한다.

### 되돌릴 조건

`platform` 스키마 노출 또는 RLS 검증이 MVP 속도를 과도하게 막으면, server action 중심 접근으로 클라이언트 직접 Data API 접근을 줄인다. 단, 고객 PII와 사진 private 원칙은 되돌리지 않는다.
