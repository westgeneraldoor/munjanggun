# n8n AI 연결 계획

## 목적

문장군의 기존 n8n 자동화는 버리지 않는다. 오히려 AppSheet, 솔라피, HTML 견적서, 향후 플랫폼 API를 연결하는 핵심 자동화 계층으로 본다.

이 문서는 Codex 같은 AI가 n8n을 안전하게 읽고, 설명하고, 테스트하고, 나중에 제한적으로 수정할 수 있게 만들기 위한 단계별 계획이다.

## 현재 전제

- n8n은 n8n Cloud 유료가 아니라 Vultr 서버에 직접 설치한 self-hosted 인스턴스다.
- 해당 서버는 n8n 실행뿐 아니라 현재 견적서 HTML 파일 저장/서빙도 담당한다.
- 기존 운영 흐름은 `AppSheet -> n8n -> HTML 견적서 생성 -> 솔라피 알림톡 발송`이다.
- 영업부 담당자는 AppSheet에서 `견적서 보내기` 액션을 누를 뿐, 생성된 HTML 링크를 직접 다루지 않는다.

## 핵심 원칙

1. 운영 워크플로우는 바로 수정하지 않는다.
2. 처음에는 읽기와 지도화만 한다.
3. 수정은 반드시 복사본/테스트 워크플로우에서 먼저 한다.
4. API 키나 토큰은 채팅에 붙여넣지 않는다.
5. AI가 직접 운영 알림톡, 결제 요청, 고객 데이터 전송을 실행하지 않게 한다.
6. n8n은 자동화 비서이고, 고객/견적/결제/권한의 장기 원장은 플랫폼 DB가 맡는다.

## 단계별 접근

### 1단계 - 읽기/지도화

목표:

- n8n 버전 확인
- 현재 워크플로우 목록 확인
- 견적서 발송 워크플로우 식별
- 주요 노드 순서 지도화
- AppSheet payload, HTML 생성, 솔라피 발송, 파일 저장 위치 확인

허용:

- 워크플로우 목록 조회
- 워크플로우 export
- 실행 이력 읽기
- 테스트 데이터 구조 확인

금지:

- 운영 workflow 활성/비활성 변경
- 운영 workflow node 수정
- 운영 webhook 호출
- 솔라피 실제 발송

### 2단계 - 테스트 복사본

목표:

- 기존 견적서 발송 워크플로우 복사본 생성
- 테스트 webhook 또는 test execution만 사용
- 플랫폼 Preview API로 더미 payload 전송 실험

허용:

- 복사본 workflow 생성
- 테스트 URL 호출
- 더미 고객 데이터 사용

금지:

- 실제 고객 데이터로 테스트 발송
- 운영 알림톡 템플릿 발송
- 기존 HTML 저장 위치 덮어쓰기

### 3단계 - 제한적 운영 반영

목표:

- 기존 운영 흐름은 유지하면서 마지막에 플랫폼 API 호출 가지를 하나 추가
- 실패해도 기존 알림톡/HTML 생성은 계속 동작하게 구성

반영 조건:

- 복사본 테스트 성공
- 실패 시 rollback 방법 확인
- 사용자가 최종 승인

## 연결 방식 후보

### A. n8n Public API

용도:

- workflow 목록 조회
- workflow export/import
- execution 조회
- 복사본 생성 검토

장점:

- 현재 self-hosted n8n에 가장 현실적인 관리 접근 방식
- Codex가 구조를 읽고 문서화하기 좋다

주의:

- API 키는 `X-N8N-API-KEY` 헤더로 사용한다.
- 비엔터프라이즈 API 키는 scope 제한이 약할 수 있으므로 노출하면 위험하다.
- 키는 채팅에 쓰지 않고 로컬 secret 또는 사용자가 직접 입력하는 방식으로 처리한다.

### B. n8n MCP Server Trigger

용도:

- 특정 n8n workflow를 MCP tool처럼 노출
- Codex가 정해진 테스트 workflow만 호출

장점:

- AI tool 호출 모델과 잘 맞는다.
- 운영 기능을 작은 tool 단위로 제한하기 좋다.

주의:

- MCP Server Trigger는 운영 workflow 전체 관리 API가 아니라, n8n workflow/tool을 외부 MCP 클라이언트에 노출하는 방식이다.
- 처음부터 운영 workflow를 MCP tool로 노출하지 않는다.

### C. Browser 기반 수동 점검

용도:

- 사용자가 n8n에 로그인된 브라우저를 열어주고 Codex가 화면을 보며 구조를 파악

장점:

- API 키 없이 시작 가능
- 사용자가 보는 화면 기준으로 천천히 진행 가능

주의:

- 수정/저장/실행 버튼은 사용자의 명시 승인 없이 누르지 않는다.

## 서버와 저장소 판단

### Vultr

현재 역할:

- n8n 실행
- HTML 견적서 저장/서빙

판단:

- 당장 유지한다.
- n8n이 이미 정상 작동 중이면 이전보다 백업/문서화/모니터링을 먼저 한다.

### Supabase

가능한 역할:

- 고객/견적/결제/상태 데이터 저장
- 견적 원장 또는 플랫폼 고객 허브 데이터 저장
- Storage로 파일 저장/서빙

주의:

- 개인정보가 들어간 HTML 견적서를 public storage에 그대로 올리는 방식은 장기적으로 조심해야 한다.
- 더 좋은 방향은 HTML 파일 저장보다 DB 데이터를 기반으로 플랫폼 페이지를 렌더링하는 것이다.

### 추천 장기 구조

```text
Vultr
-> n8n 실행

Supabase
-> 고객/견적/결제/상태 데이터

Vercel Next.js
-> 고객 견적/결제 허브 화면

Storage
-> 첨부파일, 백업 HTML, 공개 가능한 정적 파일
```

## 첫 실행 체크리스트

- [ ] n8n 접속 URL 확인
- [ ] n8n 버전 확인
- [ ] 백업 방식 확인
- [ ] API 접근 가능 여부 확인
- [ ] API 키를 채팅에 노출하지 않는 전달 방식 결정
- [ ] 견적서 발송 workflow 이름 확인
- [ ] 운영 workflow export 또는 스크린샷 기반 구조 파악
- [ ] 테스트 복사본 생성 가능 여부 확인

## 첫 질문

n8n에 접근하는 첫 방식은 아래 중 하나로 정한다.

1. 사용자가 n8n URL을 알려주고 브라우저 로그인 화면을 열어준다.
2. 사용자가 n8n API 키를 로컬 secret 방식으로 등록한다.
3. 먼저 n8n 화면 캡처/워크플로우 export 파일을 제공한다.

추천은 1번이다. 처음에는 화면을 같이 보면서 읽기만 하는 것이 가장 덜 무섭다.
