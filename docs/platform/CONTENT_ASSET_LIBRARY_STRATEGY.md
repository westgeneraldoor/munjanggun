# CONTENT_ASSET_LIBRARY_STRATEGY - 문장군 사진보관함 전략

## 0. 결론

문장군은 사진을 블로그 글에 딸린 첨부파일로 관리하지 않는다.

문장군 사진은 블로그, 시공사례, 지역 페이지, 제품 페이지, 인스타 카드뉴스, 릴스 썸네일, 상담 자료, 상세페이지에서 반복해서 쓰이는 **공용 콘텐츠 자산**이다.

따라서 다음 단계는 기존 블로그 에디터의 이미지 슬롯을 조금 고치는 것이 아니라, 문장군 전체가 함께 쓰는 **사진보관함**을 설계하는 것이다.

첫 사용처는 블로그 에디터다. 하지만 내부 구조는 블로그 전용이 아니라 문장군 전체 공용 자산 라이브러리로 둔다.

```text
사진보관함
-> 여러 장 업로드
-> 서버 자동 최적화
-> 설명/분류/태그 정리
-> 블로그 본문에 넣기
-> 이후 다른 콘텐츠에서도 재사용
```

## 1. 왜 사진을 공용 자산으로 봐야 하는가

문장군 콘텐츠의 설득력은 말보다 실제 집 사진에서 나온다.

고객이 보고 싶은 것은 제품 코드가 아니라 다음과 같은 장면이다.

- 우리 집과 비슷한 현관
- 중문이 들어가기 전 구조
- 신발장, 스위치, 바닥 단차 같은 걸림돌
- 시공 후 밝아진 공간
- 제품 디테일과 마감
- Before/After 변화

이 사진들은 한 번만 쓰고 버릴 자료가 아니다.

예를 들어 "화이트 3연동 중문, 좁은 현관, 신발장 간섭 해결" 사진은 아래에서 모두 재사용될 수 있다.

- 블로그 문제 해결형 글
- 지역별 중문 시공 페이지
- 제품별 3연동 중문 페이지
- 인스타 카드뉴스
- 릴스 썸네일
- 상담 중 고객에게 보여주는 참고 자료
- 상세페이지 사례 섹션

그래서 사진은 `글 A에 첨부된 이미지`가 아니라 `문장군이 축적한 현장 지식의 시각 자료`로 관리해야 한다.

## 2. 기존 Content OS와의 관계

현재 Content OS MVP는 `showroom.blog_media` 중심으로 동작한다.

이 구조는 보안상 맞다.

```text
검수 전 후보 사진
-> private storage
-> 관리자 preview
-> 발행 server action
-> WebP 변환
-> public storage
-> published media
```

하지만 운영자 UX로는 무겁다. 운영자가 사진 하나를 넣기 위해 `private 후보`, `approved`, `public 승격`, `usage_status` 같은 내부 구조를 이해해야 하는 순간 글쓰기 흐름이 끊긴다.

따라서 원칙을 바꾼다.

```text
내부 보안 구조는 유지한다.
운영자 화면에서는 사진보관함 언어만 보여준다.
```

기존 `blog_media`는 Content OS MVP 호환을 위해 유지한다. PR-08 이후 사진보관함이 추가되더라도 바로 삭제하거나 대체하지 않는다. 먼저 사진보관함과 `blog_media`를 연결하는 bridge를 만들고, 안정화 후 발행 흐름을 점진적으로 단순화한다.

## 3. 운영자 UX와 내부 보안 구조 분리

운영자에게 보여줄 말:

- 사진보관함
- 사진 추가
- 여러 장 업로드
- 사진 설명
- 분류
- 태그
- 본문에 넣기
- 대표사진으로 사용
- 교체
- 삭제

운영자 화면에서 숨길 말:

- private 후보
- blog_media
- approved
- public 승격
- source_type
- usage_status
- object_path
- bucket

단, 숨긴다고 해서 안전장치를 없애는 것은 아니다.

서버는 계속 아래를 처리한다.

- 원본 보관
- WebP 변환
- 썸네일 생성
- EXIF 제거
- 용량 최적화
- 중복 감지 후보 계산
- 공개용 파일 관리
- 사용 이력 기록
- 공개 페이지에 비공개 원본 경로가 노출되지 않도록 보장

## 4. 사진보관함의 첫 사용처

첫 연결 지점은 블로그 에디터의 `+ 이미지` 흐름이다.

현재 흐름:

```text
이미지 슬롯
-> private 후보 업로드
-> alt/caption/source label
-> 개인정보 확인
-> 홍보동의 확인
-> approved
-> image block 연결
```

목표 흐름:

```text
+ 이미지
-> 사진보관함 열림
-> 업로드 또는 기존 사진 선택
-> 본문에 넣기
-> 이미지 카드가 본문에 들어감
-> 위아래 이동
```

블로그 작성자는 글의 흐름에 맞는 위치에 이미지를 넣는 데 집중한다. 업로드, 변환, 파일 보안, 공개용 이미지 준비는 시스템이 처리한다.

## 5. 재사용 가능성

사진보관함은 초기에는 블로그에서만 노출되더라도, 설계는 다음 사용처를 고려한다.

| 사용처 | 재사용 방식 |
|---|---|
| 블로그 | 본문 이미지 카드, 대표사진, Q&A 보조 이미지 |
| 시공사례 | Before/After, 제품 디테일, 현장 변수 설명 |
| 지역 페이지 | 지역별 대표 사례와 분위기 사진 |
| 제품 페이지 | 3연동, 원슬라이딩, ABS도어 등 제품별 실제 적용 사진 |
| 인스타 카드뉴스 | 첫 장 썸네일, 문제 해결 장표, 사례 장표 |
| 릴스 | 썸네일, 전후 비교 컷 |
| 상담 자료 | 고객과 비슷한 현장 사례 보여주기 |
| 상세페이지 | 신뢰 섹션, 실제 시공 사례, 리뷰 보조 이미지 |

이 재사용을 위해 사진에는 최소한 아래 정보가 붙어야 한다.

- 사진 설명
- 분류
- 태그
- 제품군
- 공간 유형
- 지역
- 사용 목적
- 사용 횟수
- 원본/웹용/썸네일 파일 관계

## 6. 설계 원칙

1. 사진보관함은 문장군 전체 공용 자산이다.
2. 첫 사용처는 블로그 에디터다.
3. 사진은 글에 종속되지 않는다.
4. 한 사진은 여러 글, 페이지, 카드뉴스, 릴스, 쇼룸에서 재사용될 수 있다.
5. 업로드 후 서버가 WebP 변환, 썸네일 생성, EXIF 제거, 용량 최적화를 처리한다.
6. 운영자 화면에는 내부 storage/RLS/status 용어를 노출하지 않는다.
7. 기존 `blog_media`는 Content OS MVP 호환을 위해 유지하고, 사진보관함과 점진적으로 연결하거나 대체한다.
8. 고객명, 전화번호, 상세 주소, 상담 원문, 원본 현장 사진 같은 민감정보는 문서와 공개 콘텐츠에 넣지 않는다.
9. 실제 공개 사용은 운영자 확인과 server-side 검증을 통과해야 한다.

## 8. 성공 기준

PR-07 이후 구현이 시작될 때 다음 문장이 흔들리지 않아야 한다.

```text
운영자는 사진보관함에서 사진을 고르고,
시스템은 보안, 변환, 공개 준비를 맡는다.
```

사진보관함의 성공은 DB 구조가 멋진지가 아니라, 블로그 작성자가 사진을 넣을 때 더 이상 `private 후보`나 `public 승격`을 떠올리지 않아도 되는지로 판단한다.
