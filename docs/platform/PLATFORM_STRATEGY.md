# 문장군 플랫폼 전략

## 0. 북극성

문장군 플랫폼의 목적은 쇼핑몰이 아니라 고객 여정 통합이다.

문장군의 핵심 상품은 제품 카드가 아니다. 문장군의 핵심 자산은 무료 방문실측, 전문 매니저 상담, 정확한 견적, 전속 시공팀, A/S까지 이어지는 신뢰 프로세스다.

따라서 플랫폼은 상품을 담는 장바구니가 아니라 아래 흐름을 하나로 묶는 고객 포털이어야 한다.

```text
무료 실측 신청
→ 담당자 배정
→ 상담/실측
→ 견적
→ 결제
→ 시공
→ A/S
```

앞으로 어떤 기능을 제안하더라도 이 질문을 통과해야 한다.

> 이 기능이 무료실측부터 결제까지의 고객 여정을 더 쉽고, 더 신뢰 가능하고, 더 운영 가능하게 만드는가?

대답이 아니면 만들지 않는다.

## 1. 왜 플랫폼인가

현재 문장군의 고객 경험은 여러 채널에 나뉘어 있다.

| 채널 | 현재 역할 | 한계 |
|---|---|---|
| 네이버예약 | 무료 실측 접수 | 접수 이후 고객 여정이 문장군 자산으로 쌓이지 않음 |
| 네이버 브랜드스토어 | 결제 | 견적, 상담, 실측 맥락과 분리됨 |
| 전화 | 상담 | 기록과 상태 추적이 약함 |
| 카카오톡 | 링크 공유, 상담 보조 | 대화가 흩어지고 담당자/고객/대표가 같은 상태를 보기 어려움 |
| AppSheet | 내부 운영 전산 | 고객이 직접 보는 포털은 아님 |
| 디지털 컬러북 | 컬러 확신 제공 | 신청, 견적, 결제까지 이어지는 고객 포털은 아님 |

플랫폼을 만드는 이유는 네이버를 당장 버리기 위해서가 아니다.

플랫폼을 만드는 이유는 고객 여정의 기준점을 문장군 내부에 만들기 위해서다. 네이버는 유입과 보조 채널로 남을 수 있지만, 고객의 신청, 상담, 견적, 결제, 상태 이력은 장기적으로 문장군 플랫폼에 쌓여야 한다.

## 2. 고객 관점: 왜 플랫폼에서 무료실측을 신청하는가

고객은 "문장군이 플랫폼을 만들었기 때문에" 플랫폼을 쓰지 않는다.

고객이 플랫폼을 쓰는 이유는 네이버예약보다 더 편하거나, 더 안심되거나, 더 명확해야 한다.

### 고객에게 제공해야 하는 즉시 가치

| 가치 | 설명 |
|---|---|
| 한 번에 신청 | 이름, 연락처, 주소, 제품군, 희망 일정, 현장 사진을 한 화면에서 제출 |
| 사진 기반 사전 상담 | 방문 전 현장 사진을 올려 "우리 집도 가능한가" 불안을 줄임 |
| 담당자 연결 | 신청 후 담당 매니저가 배정되고, 고객은 누가 담당하는지 알 수 있음 |
| 견적 보관 | 카카오톡 대화 속 이미지가 아니라 본인 견적 링크로 다시 확인 |
| 결제 연결 | 결정 후 결제가 따로 흩어지지 않고 견적 흐름에서 이어짐 |
| 상태 확인 | 접수, 배정, 실측 예정, 견적 발송, 결제 대기 같은 진행 상태를 확인 |

### 고객에게 하면 안 되는 것

| 금지 | 이유 |
|---|---|
| 쇼핑몰처럼 제품을 고르게 만들기 | 문장군 구매는 실측과 상담이 먼저다 |
| 가입부터 강요하기 | 고객은 무료실측을 신청하러 왔지 회원이 되러 온 것이 아니다 |
| 장바구니/쿠폰/포인트를 앞세우기 | 가격 쇼핑몰처럼 보이면 문장군의 전문 상담 강점이 흐려짐 |
| 자동 견적을 성급히 제공하기 | 현장 특이사항과 추가금 구조가 핵심 신뢰 요소라 수동 확인이 먼저다 |

### 고객 전환 문장

플랫폼의 고객 CTA는 이렇게 말해야 한다.

```text
사진과 주소를 남겨주시면 담당 매니저가 현장 조건을 먼저 확인하고 무료 실측 일정을 안내드립니다.
```

핵심은 "가입하세요"가 아니라 "우리 집도 가능한지 먼저 확인받으세요"다.

## 3. 영업 매니저 관점: 왜 플랫폼을 쓰는가

영업 매니저는 새 시스템을 좋아해서 쓰지 않는다. 현장 업무가 줄거나, 상담 품질이 올라가거나, 놓치는 고객이 줄어야 쓴다.

### 영업 매니저에게 제공해야 하는 가치

| 가치 | 설명 |
|---|---|
| 사전 정보 확보 | 방문 전 주소, 제품군, 희망 일정, 현장 사진을 한 번에 확인 |
| 담당 고객 큐 | 오늘 연락해야 할 고객, 실측 예정 고객, 견적 대기 고객을 한 화면에서 확인 |
| 상담 맥락 보존 | 카카오톡/전화에 흩어진 정보를 견적과 함께 보관 |
| 견적 작성 시간 단축 | 제품, 옵션, 추가금, 메모를 구조화해 견적 링크로 발송 |
| 실수 감소 | 담당자 배정, 상태 변경, 견적 발송 누락을 줄임 |
| 인수인계 가능 | 담당자 부재 시에도 고객 상태를 회사가 파악 가능 |

### 영업 매니저가 싫어할 위험

| 위험 | 방어 원칙 |
|---|---|
| 입력 업무가 늘어남 | 고객이 입력한 정보를 재사용해야 함 |
| AppSheet와 이중 입력 | 플랫폼과 AppSheet의 역할을 명확히 나눠야 함 |
| 견적 작성이 복잡함 | 첫 버전은 자유 메모와 간단 항목 중심으로 시작 |
| 현장 예외를 못 담음 | 옵션보다 메모와 추가금 설명 필드를 넉넉히 둠 |

영업 매니저용 MVP는 거창한 CRM이 아니다. 첫 목표는 "접수된 무료실측 신청을 보고, 담당자를 배정하고, 고객에게 연락할 수 있는 상태"다.

## 4. 대표 관점: 왜 플랫폼을 쓰는가

대표에게 플랫폼의 가치는 "앱이 하나 더 생긴다"가 아니다.

대표에게 플랫폼은 고객 여정의 소유권, 데이터, 운영 통제력을 확보하는 장치다.

### 대표에게 제공해야 하는 가치

| 가치 | 설명 |
|---|---|
| 채널 독립성 | 네이버예약/브랜드스토어에만 의존하지 않는 자사 고객 접점 확보 |
| 퍼널 가시화 | 신청 수, 배정 수, 견적 수, 결제 전환율을 확인 |
| 담당자 운영 관리 | 누가 어떤 고객을 맡고 어디서 막혔는지 확인 |
| 리뷰/콘텐츠 자산 연결 | 시공 사진, 고객 사례, 컬러북 콘텐츠가 플랫폼 자산으로 쌓임 |
| 결제 흐름 통합 | 견적과 결제가 분리되지 않아 전환 추적이 쉬워짐 |
| 장기 OS 기반 | 고객, 영업, 제작, 시공, A/S를 연결할 토대 확보 |

### 대표 관점의 성공 기준

초기 성공은 기능 개수가 아니라 아래 질문에 답할 수 있는지로 판단한다.

| 질문 | 의미 |
|---|---|
| 이번 주 무료실측 신청이 몇 건 들어왔는가 | 유입과 CTA 검증 |
| 신청 고객 중 담당자 배정이 몇 건 되었는가 | 내부 처리 검증 |
| 배정 후 첫 연락까지 얼마나 걸렸는가 | 영업 속도 검증 |
| 견적 발송까지 몇 건 이어졌는가 | 실측 이후 전환 검증 |
| 견적에서 결제까지 몇 건 이어졌는가 | 플랫폼의 사업 가치 검증 |

## 5. 네이버에서 플랫폼으로 전환하는 순서

네이버를 한 번에 끊지 않는다.

전환은 고객 리스크를 줄이면서 단계적으로 한다.

### Phase 0: 네이버 유지 + 플랫폼 준비

| 항목 | 방향 |
|---|---|
| 네이버예약 | 유지 |
| 브랜드스토어 | 유지 |
| 디지털 컬러북 | 유지 |
| 플랫폼 | 전략 문서, 최소 DB/RBAC 설계, 로그인 준비 |

목표는 기존 매출 흐름을 건드리지 않고 플랫폼의 첫 접수 경로를 준비하는 것이다.

### Phase 1: 무료실측 신청을 플랫폼에 열기

| 항목 | 방향 |
|---|---|
| 기본 CTA | 플랫폼 무료실측 신청 |
| 네이버예약 | 보조/대체 경로로 유지 |
| 고객 입력 | 이름, 전화번호, 주소, 제품군, 희망 일정, 현장 사진 |
| 내부 확인 | 관리자/영업 매니저가 접수 목록 확인 |

이 단계의 목표는 실제 고객 신청이 플랫폼으로 들어오는지 확인하는 것이다.

### Phase 2: 담당자 배정과 상담 상태를 플랫폼에 넣기

| 항목 | 방향 |
|---|---|
| 관리자 | 접수 건을 매니저에게 배정 |
| 매니저 | 담당 고객 큐 확인 |
| 고객 | 접수/배정/실측 예정 상태 확인 |
| AppSheet | 기존 운영 전산과 역할 분리 또는 연동 방식 결정 |

이 단계의 목표는 플랫폼이 단순 폼이 아니라 운영 흐름의 일부가 되는 것이다.

### Phase 3: 견적 링크를 플랫폼으로 발송

| 항목 | 방향 |
|---|---|
| 매니저 | 제품, 옵션, 추가금, 메모로 견적 생성 |
| 고객 | 본인 견적 링크 조회 |
| 관리자 | 전체 견적 상태 확인 |
| 결제 | 아직 브랜드스토어 병행 가능 |

이 단계의 목표는 견적이 카카오톡 이미지/텍스트가 아니라 플랫폼 문서로 남는 것이다.

### Phase 4: 결제를 견적 흐름에 연결

| 항목 | 방향 |
|---|---|
| 결제 | 토스페이먼츠 도입 |
| 브랜드스토어 | 필요 시 병행, 점진 축소 |
| 상태 | 견적발송 → 결제대기 → 결제완료 |
| 지표 | 견적→결제 전환율 측정 |

이 단계에서야 플랫폼은 네이버 브랜드스토어 일부 역할을 대체한다.

## 6. MVP 실행 원칙

문서만 오래 쓰지 않는다.

다만 개인정보와 권한이 들어가는 순간 최소한의 DB/RBAC 설계는 필요하다. 그래서 순서는 아래처럼 잡는다.

```text
1. 최소 DB/RBAC 설계
2. OAuth 로그인
3. 무료실측 신청 구현
4. 접수 목록/담당자 배정
5. 견적 생성
6. 결제 연결
```

여기서 "최소 DB/RBAC 설계"는 거대한 설계 프로젝트가 아니다.

첫 구현에 필요한 범위만 정한다.

| 설계 항목 | 첫 범위 |
|---|---|
| 사용자 | customer, sales_manager, administrator |
| 인증 | 카카오/네이버/구글 OAuth 중 실제 우선순위 확정 |
| 신청 | 이름, 전화번호, 주소, 제품군, 희망 일정, 사진 |
| 권한 | 고객은 본인 신청만, 매니저는 담당 신청만, 관리자는 전체 |
| 사진 | 고객 현장 사진은 공개 버킷 금지 |
| 상태 | 접수대기, 담당자배정, 실측예정, 실측완료 |

이 정도가 정리되면 바로 MVP-01 로그인과 MVP-02 무료실측 신청으로 들어간다.

## 7. 첫 번째 플랫폼 화면의 기준

첫 번째 플랫폼 화면은 예쁜 대시보드가 아니다.

첫 번째 플랫폼 화면은 고객이 실제로 무료실측을 신청하는 화면이다.

필수 입력:

| 필드 | 이유 |
|---|---|
| 이름 | 담당자 연락과 견적 식별 |
| 전화번호 | 실제 상담 연락 |
| 주소 | 서비스 가능 지역과 현장 조건 판단 |
| 제품군 | 중문/도어/현관문 등 상담 분류 |
| 희망 일정 | 실측 일정 조율 |
| 현장 사진 | 방문 전 가능 여부와 특이사항 예측 |

성공 기준:

| 기준 | 설명 |
|---|---|
| 고객이 1~2분 안에 신청 완료 | 폼 마찰 최소화 |
| 신청 후 고객이 다음 단계를 이해 | "담당 매니저가 연락드립니다"가 명확해야 함 |
| 관리자/매니저가 접수 건 확인 | 실제 운영이 시작되어야 함 |
| 사진이 안전하게 저장 | 공개 쇼룸 이미지와 다른 보안 정책 적용 |

## 8. 기능 컷 기준

아래 기능은 플랫폼의 북극성과 어긋나므로 MVP에서 만들지 않는다.

| 기능 | 컷 이유 |
|---|---|
| 장바구니 | 고객 여정이 실측 전 상품 구매로 오해됨 |
| 쿠폰/포인트 | 가격 쇼핑몰처럼 보이고 상담 중심 모델을 흐림 |
| 회원등급 | 시공 고객 포털 초기 가치와 무관 |
| 리뷰 작성 기능 | 이미 네이버 리뷰 자산이 있고 MVP 핵심 아님 |
| 자동 견적 엔진 | 현장 변수와 신뢰 리스크가 큼 |
| 제품 검색/필터 고도화 | 무료실측 접수 검증 전에는 후순위 |
| 커뮤니티/댓글 | 상담 채널 분산을 다시 만들 수 있음 |

보류 기능을 다시 검토하려면 아래 질문을 통과해야 한다.

1. 무료실측 신청 수를 늘리는가?
2. 담당자 배정과 첫 연락을 빠르게 하는가?
3. 견적 작성 시간을 줄이는가?
4. 견적에서 결제까지의 전환을 높이는가?
5. 대표가 운영 상태를 더 잘 보게 하는가?

## 9. 문서 우선순위

플랫폼 작업의 문서 우선순위는 다음과 같다.

두 문서가 충돌하면 전략 문서가 우선한다.

## 10. 최종 전략 문장

문장군 플랫폼은 쇼핑몰이 아니다.

문장군 플랫폼은 고객이 무료실측을 신청하고, 담당자와 연결되고, 견적을 확인하고, 결제까지 진행하는 고객 여정 통합 포털이다.

기존 디지털 컬러북은 이 포털의 Public Experience로 남는다.

네이버는 당장 버릴 대상이 아니라 단계적으로 역할이 줄어드는 외부 채널이다.

첫 번째 MVP의 목적은 완벽한 운영 OS가 아니라, 실제 고객이 플랫폼에서 무료실측을 신청하고 회사가 그 신청을 처리할 수 있음을 증명하는 것이다.
